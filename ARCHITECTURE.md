# Архитектурные решения

Краткое описание того, что и почему сделано именно так в рамках тестового задания «АвтоЗапчасти».

---

## Задание 1 — Каталог товаров

### Собственные компоненты вместо bitrix:catalog

Решено писать `autoparts:catalog` и `autoparts:catalog.detail` с нуля, а не наследовать/копировать `bitrix:catalog.section` + `bitrix:catalog.element`.

**Почему:** задание требует «собственный шаблон» и проверяет понимание API Битрикса, а не умение настраивать готовый компонент. Свой компонент даёт полный контроль над выборкой данных, кэшем и AJAX-логикой без борьбы с параметрами штатного компонента, заточенного под полноценный модуль `catalog` (торговые предложения, цены, скидки), которые в задании не требуются.

**От чего отказались:** не стали подключать модуль `catalog` (торговый каталог с ценами/скидками) — инфоблок «Каталог автозапчастей» используется как простой информационный блок со свойством `PRICE`. Полноценный каталог с ценовыми типами избыточен для объёма задания и усложнил бы интеграцию с заданием 3 (создание заказа).

### Логика в class.php, а не в template.php

Вся выборка данных, фильтрация и кэширование — в `class.php` (наследник `CBitrixComponent`). Шаблон (`template.php`) только выводит готовый `arResult`.

**Почему:** разделение ответственности — шаблон отвечает за вёрстку, класс компонента за данные. Это позволяет менять дизайн без риска сломать логику и наоборот.

### Кэширование через startResultCache/endResultCache

Используется стандартный механизм Битрикса с динамическим `cacheId`, построенным из параметров фильтра:

```php
$cacheId = md5(serialize($filter) . $pageSize . $pageNum);
```

**Почему:** каждая уникальная комбинация фильтра (бренд + цена + наличие) кэшируется отдельно — это даёт реальный прирост производительности при повторных запросах с одинаковыми параметрами, в отличие от кэширования всей страницы целиком.

**От чего отказались:** не использовали тегированное кэширование через `CacheManager::registerTag()` — в установленной версии модуля `main` этот метод недоступен в публичном API (`Call to undefined method`). Сброс кэша происходит штатным механизмом Битрикса при изменении элементов инфоблока через админку (стандартное поведение `iblock`), либо по истечении `CACHE_TIME`.

### AJAX без фреймворков (vanilla JS)

Фильтр реализован на чистом JS с `fetch()` и `history.pushState()`, без jQuery/Vue.

**Почему:** задача простая (один фильтр, одна зона обновления), подключать фреймворк ради этого избыточно. Vanilla JS также гарантирует отсутствие конфликтов с другими скриптами на странице (важный критерий оценки).

## Задание 2 — Импорт из 1С

### Поиск товаров по артикулу, а не по XML_ID

При синхронизации существующий товар определяется по значению свойства `PROPERTY_ARTICLE`, а не по системному полю `XML_ID`.

**Почему:** по условию задания «существующие (по артикулу как XML_ID)» — то есть артикул и есть идентификатор для сопоставления. На практике поле `XML_ID` в админке Битрикса недоступно для редактирования через стандартную форму без модуля `catalog`/доп. настроек, тогда как `PROPERTY_ARTICLE` — обычное пользовательское свойство, которое мы полностью контролируем.

### XMLReader вместо SimpleXMLElement

Парсинг XML переведён с `simplexml_load_file()` (загружает весь файл в память) на потоковый `XMLReader` с `expand()` для каждого узла `<Товар>`.

**Почему:** требование задания — «корректно работать с выгрузкой 5000+ позиций». `simplexml_load_file` держит весь DOM в памяти, что для больших выгрузок 1С (десятки тысяч позиций) может превысить `memory_limit`. `XMLReader` читает файл последовательно, расходуя память только на текущий обрабатываемый узел.

### Обработка пакетами (batch) с паузой

Товары делятся на пакеты по 50 штук (`array_chunk`), между пакетами — пауза 50ms (`usleep`).

**Почему:** при импорте тысяч позиций один сплошной цикл может: (1) упереться в `max_execution_time` при запуске не из консоли, (2) создать нагрузку на БД конкурирующими блокировками таблиц `b_iblock_element`. Пауза между пакетами даёт БД время обработать другие запросы (если импорт идёт параллельно с живым трафиком сайта).

### Try/catch на каждый товар

Каждая операция создания/обновления товара обёрнута в `try/catch` внутри цикла, а не вокруг всего импорта.

**Почему:** прямое требование задания — «не падать на одной плохой записи». Если бы `try/catch` стоял вокруг всего цикла, одна ошибка (например, незаполненный артикул у одной позиции) прервала бы обработку всех оставшихся 4999 товаров.

### Деактивация через CIBlockElement::Update, а не D7 ElementTable::update

Изначально деактивация была написана на D7 (`ElementTable::update()`), но Битрикс выбросил ошибку: «Для изменения элементов инфоблоков используйте вызов CIBlockElement::Update()».

**Почему перешли на старый API:** в этой версии модуля `iblock` запись через чистый D7 `ElementTable` заблокирована намеренно — Битрикс требует использовать `CIBlockElement`, так как у него есть дополнительная бизнес-логика (события `OnBeforeIBlockElementUpdate`, пересчёт поискового индекса и т.д.), которую прямой `UPDATE` через D7-таблицу обошёл бы. Чтение (`GetList`) оставлено через старый `CIBlockElement::GetList`, так как именно он отдаёт значения свойств (`PROPERTY_ARTICLE_VALUE` и т.д.) без дополнительных JOIN-ов, которые требовались бы при D7.

### Логирование в файл, а не в БД

Лог пишется построчно в `/upload/1c_import/logs/import_YYYY-MM-DD.log` через `file_put_contents(..., FILE_APPEND)`.

**Почему:** для разового консольного скрипта, запускаемого по cron, текстовый лог проще для администратора (можно `tail -f` в реальном времени) и не создаёт нагрузку на БД во время самого импорта. Отдельная таблица логов в БД была бы избыточна для задачи такого масштаба.

## Задание 3 — REST API

### Собственный роутер вместо bitrix:rest

Прямое требование задания — «не штатный bitrix:rest». Реализован простой роутер (`api/v1/index.php`), который разбирает `REQUEST_URI` и вызывает соответствующий контроллер.

**Почему именно так, а не модуль:** формальный модуль Битрикса (с `install/`, `.settings.php`, регистрацией в реестре) добавляет инфраструктурный код, не несущий ценности для тестового задания такого объёма. Текущая реализация — обычные PHP-классы с автозагрузкой через `Loader::registerAutoLoadClasses()`, что Битрикс поддерживает «из коробки» без необходимости создавать полноценный модуль.

### Хранение токенов в собственной таблице, а не в UF-поле пользователя

Решено создать таблицу `autoparts_api_token` вместо хранения токена в пользовательском поле (`UF_API_TOKEN`).

**Почему:** пользовательское поле хранит одно значение на пользователя — если пользователь авторизуется с двух устройств (телефон + планшет), второй логин перезатрёт токен первого устройства. Отдельная таблица позволяет хранить **несколько активных токенов** на одного пользователя, у каждого — собственное время жизни, что ближе к поведению реальных мобильных приложений.

### Время жизни токена — 24 часа, без refresh-токена

**Почему:** задание просит «сохраняйте токен... со временем жизни» — минимальное жизнеспособное решение. Полноценная пара access/refresh токенов — стандартная практика, но усложняет API сверх того что просит задание. При необходимости пользователь просто повторно логинится через `/auth/token`.

**От чего отказались:** не реализован эндпоинт `/auth/refresh` — это следующий логичный шаг для продакшен-версии, но не входил в минимальный набор эндпоинтов задания.

### Единый ApiResponse и глобальный exception handler

Все контроллеры возвращают ответ только через статические методы `ApiResponse::success()` / `ApiResponse::error()`. В роутере установлен `set_exception_handler` и `set_error_handler`.

**Почему:** требование задания — «единый формат ошибок». Без глобального перехвата исключений непойманная ошибка PHP (например, Fatal Error в стороннем коде Битрикса) отдала бы клиенту HTML страницу с ошибкой вместо JSON, что сломало бы клиент мобильного приложения, ожидающий строго JSON на любой ответ сервера.

### Создание заказа через Bitrix\Sale\Order (D7), не CSaleOrder

**Почему:** прямое требование задания — «использовать API модуля sale (Bitrix\Sale\Order)». Старый `CSaleOrder` считается устаревшим, новый D7 `Order`/`Basket` — текущий рекомендованный способ создания заказов в Битриксе, с явным разделением «корзина → заказ» и понятным API для работы с состоянием.

### Проверка наличия товара до создания заказа

В `OrderController` перед добавлением товара в корзину проверяется `IN_STOCK >= quantity`. При нехватке — `409 OUT_OF_STOCK`, заказ не создаётся.

**Почему:** мобильное приложение может отправить заказ на товар, который закончился между показом каталога и нажатием «Купить» (race condition при параллельных заказах). Серверная проверка — последний рубеж защиты от продажи отсутствующего товара.

## Общие решения по безопасности

- Все значения, выводимые в HTML-шаблонах (`template.php`), экранируются через `htmlspecialchars()`.
- Доступ к `/run_import.php` (запуск импорта через браузер) ограничен проверкой `$USER->IsAdmin()`.
- В `ApiToken::validate()` SQL-параметр токена экранируется через `$connection->getSqlHelper()->forSql()` перед вставкой в запрос (защита от SQL-инъекций при ручной сборке запроса).
- Bearer-токен передаётся только в заголовке `Authorization`, не в query-string — снижает риск утечки токена через логи веб-сервера.
- Эндпоинт создания заказа (`order/create`) требует валидный токен — анонимные заказы через API невозможны.

## Что было бы сделано иначе в продакшен-версии

Если бы это был не тестовый, а реальный production-проект — добавили бы:

1. **Refresh-токены** и возможность отозвать токен (logout).
2. **Rate limiting** на `/auth/token` — защита от подбора пароля.
3. **Полноценный модуль catalog** с ценовыми типами и скидками вместо простого инфоблока с числовым свойством цены.
4. **Очередь (RabbitMQ/Redis)** для импорта из 1С вместо синхронного cron-скрипта — при объёме 50 000+ позиций синхронный импорт даже пакетами может не укладываться в окно cron.
5. **Версионирование API** не только в URL (`/v1/`), но и через заголовок `Accept`, для более гибкой поддержки нескольких версий мобильного приложения одновременно.
